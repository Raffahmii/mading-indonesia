Siap bre. Gue nangkep konsep besarnya. Ini **bukan sekadar mading CRUD biasa**, tapi lebih tepatnya **platform mading/informasi antar-universitas di Indonesia** dengan model multi-university, role-based access, approval workflow, dan **dynamic university branding**.

Sebelum masuk ERD/SQL/coding, menurut gue memang paling aman kita **kunci dulu product concept + UI/UX + business rules**. Setelah itu baru diturunkan ke database supaya dari awal nggak ada struktur yang nanti harus bongkar ulang.

## 1. Konsep inti yang gue tangkap

Nama sementara misalnya:

> **MADING INDONESIA**
> *Pusat Informasi dan Mading Antar-Universitas Indonesia*

Platform ini menjadi tempat berbagai universitas di Indonesia untuk mempublikasikan informasi seperti:

* Pengumuman universitas
* Pendaftaran mahasiswa
* Event kampus
* Lomba
* Seminar
* Workshop
* Beasiswa
* Prestasi
* Hasil lomba
* Organisasi/kegiatan mahasiswa
* Informasi akademik
* Informasi non-akademik
* Dan konten lain yang relevan

Tetapi yang membedakan dari website berita biasa adalah:

> **Setiap universitas memiliki ruang/tenant sendiri, admin sendiri, identitas visual sendiri, tetapi semuanya berada di dalam satu platform nasional.**

Jadi misalnya:

```text
                 MADING INDONESIA
                        │
       ┌────────────────┼────────────────┐
       │                │                │

       │                │                │
```

Sementara anggota biasa:

# 2. Tiga Role Utama

## SUPER ADMIN

Ini adalah pihak yang mengelola **platform secara keseluruhan**.

Super Admin bukan admin sebuah universitas.

Dia berada di level:

```text
PLATFORM
   │
   └── SUPER ADMIN
```

Super Admin dapat:

* Login
* Dashboard platform
* CRUD universitas
* Membuat universitas baru
* Menentukan nama universitas
* Menentukan logo universitas
* Menentukan warna/brand universitas
* Membuat akun admin universitas
* Mengaktifkan/nonaktifkan universitas
* Mengubah data universitas
* Mengatur admin universitas
* Melihat seluruh konten
* Melakukan approval/rejection konten
* Menghapus konten bermasalah
* Mengelola anggota
* Melihat statistik platform
* Mengelola kategori
* Mengontrol status publikasi
* Dan fungsi administratif lainnya

### Hal penting

Super Admin **tidak perlu menggunakan warna universitas**.

Dashboard Super Admin menggunakan **brand utama platform**.

# 6. Konsep Approval yang Penting

Nah, bagian ini menurut gue **harus kita masukkan dari awal ke arsitektur sistem.**

Admin universitas **tidak langsung publish**.

Flow-nya:

```text
ADMIN UNIVERSITAS
       │
       ▼
Create Content
       │
       ▼
     DRAFT
       │
       ▼
 Submit for Approval
       │
       ▼
    PENDING
       │
       ▼
   SUPER ADMIN
       │
    ┌──┴───┐
    ▼      ▼

    │      │
    ▼      ▼
PUBLISHED  REVISION
```

Jadi Admin ITB misalnya membuat:

> "ITB Mengadakan Lomba Programming Nasional 2026"

```text

```

Kalau bagus:

```text

     ↓
PUBLISHED
```

Kalau ada masalah:

```text

     ↓
Admin ITB melakukan revisi
     ↓
Submit ulang
```

Ini memenuhi requirement:

> "admin nggak bisa langsung sembarang posting."

# 9. Jangan Hardcode Warna di Blade

Ini penting untuk implementasi Laravel nanti.

Jangan:

```html
<div class="bg-blue-600">
```

untuk dashboard universitas.

Karena warna harus dynamic.

Konsepnya nanti:

```php
$university->primary_color
$university->secondary_color
```

kemudian digunakan sebagai CSS variable:

```css
:root {
    --university-primary: ...;
    --university-secondary: ...;
}
```

Contoh:

```css
background-color: var(--university-primary);
```

Sehingga:

```text
ITB → biru
UI  → biru
UGM → merah
ITS → biru
```

tanpa membuat dashboard berbeda-beda.

# 31. FULL PROMPT MASTER — Konsep Website

Nah, kalau lu ingin memasukkan konsep ini ke AI/design generator/Figma AI atau nanti menjadi **master specification untuk DeepSeek**, prompt dasarnya bisa kita jadikan seperti ini:

Buat sebuah platform web bernama **MADING INDONESIA**, yaitu platform digital mading dan pusat informasi antar-universitas di Indonesia.

Platform ini memungkinkan berbagai universitas di Indonesia memiliki ruang informasi masing-masing dalam satu platform terpusat. Setiap universitas memiliki administrator sendiri, identitas visual sendiri, dan hanya dapat mengelola konten milik universitasnya. Pengguna umum dapat melihat seluruh informasi dari seluruh universitas.

Gunakan konsep **multi-university / multi-tenant content platform** dengan tiga role utama:

1. SUPER ADMIN
2. ADMIN UNIVERSITAS
3. ANGGOTA

==================================================
ROLE & AUTHORIZATION
====================

SUPER ADMIN:

* Mengelola seluruh platform.
* Membuat, mengubah, menghapus, mengaktifkan, dan menonaktifkan universitas.
* Menentukan nama universitas.
* Menentukan logo universitas.
* Menentukan primary color dan secondary color universitas.
* Membuat akun admin universitas.
* Mengelola seluruh admin universitas.
* Melihat dan mengelola seluruh konten.
* Melakukan approval/rejection terhadap konten yang dibuat admin universitas.
* Mengelola kategori konten.
* Mengelola anggota.
* Melihat statistik platform.
* Memiliki akses global tanpa pembatasan university scope.

ADMIN UNIVERSITAS:

* Dibuat hanya oleh Super Admin.
* Tidak memiliki halaman register.
* Terhubung secara permanen dengan satu universitas.

IMPORTANT BUSINESS RULES
========================

1. Hanya anggota yang dapat register melalui public registration.

2. Admin universitas hanya dibuat oleh Super Admin.

3. Super Admin memiliki akses global.

4. Admin universitas hanya dapat mengakses universitas yang terhubung dengan akun tersebut.

5. Admin universitas tidak dapat mengubah university_id miliknya melalui request client.

6. Admin universitas tidak dapat mengakses endpoint universitas lain hanya dengan mengubah URL atau ID.

7. Semua query admin universitas harus menggunakan university scope.

8. Konten admin universitas harus melalui approval Super Admin.

9. Konten PENDING tidak boleh tampil pada public website.

10. Konten REJECTED tidak boleh tampil pada public website.

11. Hanya konten PUBLISHED yang tampil pada public website.

12. Warna universitas harus berasal dari database.

13. Jangan hardcode university-specific color di Blade/Tailwind.

14. Semua perubahan penting harus dapat dicatat dalam activity log.

15. Semua form harus divalidasi server-side.

16. Jangan hanya mengandalkan validasi frontend.

17. Gunakan authorization policy/middleware Laravel.

18. Hindari mass assignment vulnerability.

19. Password harus disimpan menggunakan Laravel hashing.

20. Gunakan CSRF protection.

21. Gunakan pagination untuk data besar.

22. Gunakan slug untuk public URL.

23. Gunakan soft delete untuk data yang membutuhkan recovery.

24. Public user tidak dapat mengakses dashboard admin.

25. Admin tidak dapat mengakses dashboard Super Admin.

### Satu keputusan arsitektur yang menurut gue harus kita pegang dari awal

**Jangan membuat tiga aplikasi terpisah untuk Super Admin, Admin, dan Anggota.**

Tetap:

```text
                 ONE LARAVEL APPLICATION
                          │
             ┌────────────┼────────────┐
             ▼            ▼            ▼
        PUBLIC AREA   ADMIN AREA   SUPER ADMIN
             │            │            │
             │       university_id     global
             │            │
             └────────────┴────────────┘
                          │
                         MySQL
```

Jadi satu aplikasi, satu database, satu codebase, tetapi **authorization + scope + UI** yang membedakan aksesnya.

Dan konsep **dynamic university color** kita jadikan bagian resmi dari arsitektur, bukan sekadar kosmetik. Itu berarti dari database → middleware/controller → view → CSS variable → component, semuanya harus dirancang untuk mendukung theme universitas.
